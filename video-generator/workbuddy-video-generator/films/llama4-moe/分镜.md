## Scene 01｜0:00–0:20：制造悬念

**画面文字**
`400,000,000,000` Parameters
每次只激活：`17,000,000,000` Parameters
为什么？

**画面**
28×11 的参数阵列铺满画面；约 4.5% 的单元保持高亮，其余退到 12% 透明度；最后把高亮单元放大，旁边给出 17B。

**字幕**
400B 总参数，为什么每次只激活 17B？

**旁白**
一个拥有 4000 亿参数的大模型，为什么每次处理 Token 时，只需要激活约 170 亿参数？
这不是简单的模型压缩，而是一种完全不同的参数使用方式。
它就是 Llama 4 Maverick 采用的混合专家架构，MoE。

## Scene 02｜0:20–0:50：为什么要研究它

**画面文字**
2023：LLaMA
2024：Llama 3.1 405B
2025：Llama 4 MoE

**画面**
时间线推进；到 405B 时，稠密 Transformer 的层堆叠不断加高；随后 FFN 被拆成一组专家模块。

**字幕**
2023 → 2025：从稠密到 MoE

**旁白**
2023 年，Meta 发布初代 LLaMA，推动了开放权重大模型生态的发展。
2024 年，Llama 3.1 已经把稠密 Transformer 扩展到 4050 亿参数。
但模型越大，计算和部署成本通常也越高。
到了 2025 年，Meta 开始探索另一种路线：不再让所有参数始终参与计算，而是根据输入动态选择其中一部分。

## Scene 03｜0:50–1:30：Dense 与 MoE 的区别

**画面文字**
Dense：All Tokens → Same FFN
MoE：Each Token → Selected Experts

**画面**
左侧：多个 Token 依次通过单一 FFN。
右侧：FFN 拆成多个 Expert，来自不同位置的 Token 被 Router 分配到不同计算路径。

**字幕**
Dense：所有 token 走同一个 FFN；MoE：每个 token 走被选中的专家

**旁白**
传统 Transformer 中，每个 Token 会通过同一层相同的前馈网络，也就是 FFN。
MoE 改变了这个部分。
它把单个 FFN 替换成多个拥有独立参数的专家网络。
但关键在于，并不是每次都运行所有专家。
模型会通过一个 Router，决定当前 Token 应该由哪个专家处理。
这样，模型可以拥有大量参数，但只执行其中一部分。

## Scene 04｜1:30–2:15：Router 如何工作？

**画面文字**
Router
Score → Top-1 → Selected Expert

**画面**
Token 进入 Router；三个专家的示意 logit：-0.5、0、-1.2；最大值得 0 被选中；连接线指向 Expert 2；最后展开成 128 个专家的矩阵，仅 1 个高亮。

**字幕**
Router：给 128 个专家打分，Top-1 选中一个

**旁白**
Router 的工作原理并不神秘。
它首先根据 Token 当前的隐藏状态，通过一个可学习的矩阵计算每个专家的得分。
接着，模型选择得分最高的专家。
Llama 4 Maverick 采用的是 Top-1 路由。
也就是说，在一个 MoE 层内，虽然有 128 个路由专家，但每个 Token 只选择其中一个。
而且，这种选择不是根据人工设定的关键词规则，而是由模型训练得到的路由参数和 Token 的上下文表示共同决定。

## Scene 05｜2:15–3:05：共享专家与路由专家

**画面文字**
Shared Expert：始终执行
Routed Expert：动态选择
最终输出：两条路径融合

**画面**
Token 分成两条路径：A 进入共享专家；B 经过 Router 进入选中的路由专家；两条路径汇合。画面中央给出公式。

**字幕**
共享专家 + 路由专家：两条路径相加

**公式（修正后）**
`MoE(x) = S(x) + g_j(x) · E_j(x)`
其中 `j = argmax_i sigmoid(W_r x)_i`，`g_j(x) = sigmoid(W_r x)_j`

**旁白**
但 Llama 4 还做了一件重要的事。
除了 128 个路由专家，它还有一个共享专家。
共享专家不需要经过 Router 选择，每个 Token 都会使用它。
因此，一个 Token 实际上会经过两条计算路径。
一条是共享专家，另一条是由 Router 选中的路由专家。
根据 Meta 公开代码，选中专家的路由分数会经过 Sigmoid，得到门控系数，再作用于专家的**输出**。
最后，两条路径的计算结果相加。
这就是 Llama 4 MoE 最核心的计算机制。

## Scene 06｜3:05–3:50：效果与代价

**画面文字**
400B Total
17B Active
但：
Active Parameters ≠ Memory Usage

**画面**
左侧：400B 参数池，17B 激活部分高亮。
右侧：存储、通信、负载均衡、Token 调度四个系统模块依次出现。
底部权衡关系：Model Capacity ↔ Compute ↔ Memory ↔ Communication

**字幕**
17B 激活 ≠ 17B 存储

**旁白**
这让 Llama 4 能够拥有很大的模型容量，却不必在每次计算时激活全部专家参数。
但这里有一个经常被忽略的细节。
17B 激活参数，不意味着模型只需要存储 17B 参数。
那些没有参与当前 Token 计算的专家权重，依然需要被系统管理。
如果专家分布在不同 GPU 上，还会涉及通信、负载均衡和 Token 调度。
所以 MoE 真正解决的，不是让计算成本消失，而是重新分配模型容量与计算资源。

## Scene 07｜3:50–4:50：从 Llama 到 Muse 与总结

**画面文字**
2025：Llama 4
2026：Muse
三点总结
核心研究问题：How to Scale Model Capacity Efficiently?

**画面**
Llama 4 的专家结构缩小，融入 2025–2026 时间线；随后切到三点总结；最后回到单个 Token 的完整计算路径，落到片尾标题。

**字幕**
参数可以很多，但不必全部激活

**旁白**
Llama 4 发布后，Meta 在 2026 年转向 Muse 系列。但如何用更少的计算换更强的能力，依然是大模型研究的核心问题。
回顾 Llama 4 的 MoE，可以总结三点。
第一，参数可以很多，但不必全部激活。
第二，Router 决定每个 Token 走哪条专家路径。
第三，共享专家与路由专家共同完成特征变换。
真正值得继续研究的是：增加多少专家、每次激活几个、如何安排专家层，才能得到更好的性能与效率？
这正是 MoE 架构持续演进的重要问题。

**片尾文字**
Llama 4 MoE
Scaling Capacity Without Activating Everything
